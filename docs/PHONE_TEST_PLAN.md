# План прогона на физическом телефоне

Цель: за ~1 час на реальном телефоне (4–6 ГБ RAM, arm64) получить замеры, которых нет на ПК: RTF, пиковая RAM,
стабильность (крэши/ANR/LMK), валидность JSON, поведение на «злых» файлах и форматах. По AGENTS.md §6 изменения
скорости и памяти принимаются только по замеру на телефоне.

Инструменты:
- `tools/phone_bench.sh` — автоматический прогон BenchActivity (установка, заливка, ожидание, память/температура, отчёты);
- `tools/phone_prepare.py` — собирает набор файлов и эталоны в `.cache/phone_stage/` (вызывается скриптом);
- `tools/phone_summary.py` — сводка по прогону (вызывается скриптом);
- `tools/phone_airplane_check.md` — ручной чек-лист UX в авиарежиме и сценарий «как жюри».

## Подготовка (до прихода телефона, ~5 мин)

1. APK собран: `src/android/app/build/outputs/apk/release/app-release.apk` (~1.0 ГБ).
2. `python -m pip install -r tools/requirements.txt`; при желании ffmpeg на PATH (иначе m4a/amr-варианты пропускаются).
3. Проверка без телефона: `tools/phone_bench.sh --dry-run` печатает все команды adb/python.
4. На телефоне: «Для разработчиков» → «Отладка по USB»; на Xiaomi также «Установка через USB». Зарядить ≥ 50 %, снять чехол.
5. Свободно на телефоне ≥ 3.5 ГБ (APK 1 ГБ + установка + копия LLM 0.47 ГБ во внутреннюю память при первом запуске).

## Таймлайн часа

| время | шаг | команда |
|---|---|---|
| 0–5 мин | подключение, модель/Android/RAM, установка APK | `tools/phone_bench.sh --jury` (ставит APK) |
| 5–15 мин | быстрый прогон 3 файлов «как жюри» (6.6 мин аудио) — первое значение RTF и RAM | (тот же запуск) |
| 15–40 мин | полный набор: 12 файлов `testdata/test` (31 мин аудио) + 7 «злых» + 4–6 форматов | `tools/phone_bench.sh --skip-install` |
| 40–60 мин | ручной чек-лист в авиарежиме (чистая установка, SAF, «Поделиться», микрофон, поворот, экспорт) | `tools/phone_bench.sh --manual-push`, затем `--manual-collect` |
| если осталось время | длинный файл на 30 мин — риск OOM диаризации | `tools/phone_bench.sh --skip-install --no-edge --no-fmt --exclude . --long 30` |

`--exclude .` исключает все обычные файлы (регэксп по имени), длинный файл добавляется отдельно.
При RTF 0.5 полный прогон ≈ 20 мин; если первые файлы показали RTF > 1 — сократить: `--exclude 'clip|quiet|tel8k|5spk'`.

Телефон между прогонами лучше дать остыть 2–3 мин (троттлинг искажает RTF — см. `thermal.csv`).

## Что делает phone_bench.sh

1. `adb devices`, свойства телефона (`getprop`, `/proc/meminfo`, `df /data`, `dalvik.vm.heapsize`, авиарежим) → `device.txt`.
2. `adb install -r` (при отказе потоковой установки — `push` в `/data/local/tmp` + `pm install`); проверка, что в
   установленном пакете нет `android.permission.INTERNET` (правило 1).
3. `phone_prepare.py`: копии аудио + эталоны; генерация отсутствующих «злых» файлов в `.cache/edge`
   (тишина/шум/музыка 10 с, короткое «да», стерео 48 кГц 24 бит, 8 бит 22 кГц, битый WAV);
   варианты `distinct_2spk_000` в mp3/m4a/ogg/opus/amr/flac (ffmpeg, иначе soundfile: mp3/ogg/opus/flac).
4. Очистка и заливка в `/sdcard/Android/data/ru.neurosteno.app/files/bench/`.
5. `logcat -c`, фоновый `logcat` в файл, «не гасить экран при USB» (`svc power stayon usb`, исходное значение
   восстанавливается при выходе; отключить — `--no-stayon`), `am force-stop` + `am start -n ru.neurosteno.app/.BenchActivity`.
6. Параллельно: `dumpsys meminfo` + `/proc/<pid>/status` (VmRSS, VmHWM) каждые `--interval` с → `meminfo.csv`;
   батарея/thermal HAL/частоты CPU каждые `--thermal` с → `thermal.csv`.
7. Ожидание строки `bench done` (тег `NeuroSteno`), прогресс по строкам `bench "<имя>":{...}`.
   Если процесс умер — фиксирует файл, на котором упал, переносит его в `bench/crashed/`, обработанные в `bench/done/`
   и перезапускает (до `--retries` раз). Зависание: нет прогресса `--stall` мин. Ctrl+C — прервать ожидание, собранное скачается.
8. `adb pull` → `out/phone/<дата>/out/`; при крэше — `dumpsys dropbox` (crash/anr/native).
9. `phone_summary.py --write-timings` (тайминги BenchActivity → формат report.py), `report.py` по основному набору,
   форматам и длинному файлу, затем сводка `summary.md`.

> Тайминги BenchActivity (`total_ms`, `rtf`) и report.py (`proc_ms`) несовместимы напрямую: `report.py` упадёт с
> KeyError на `out/timings.json` с телефона. Поэтому скрипт передаёт ему `timings_report.json`.
> Тайминги берутся из строк logcat — они переживают крэш посреди прогона (BenchActivity пишет `timings.json` только в конце).

Артефакты в `out/phone/<дата>/`: `device.txt`, `logcat.txt`, `events.csv`, `meminfo.csv`, `meminfo_raw.txt`,
`thermal.csv`, `out/*.json`, `bench_timings.json`, `timings_report.json`, `report_main.md|csv`, `report_fmt.md|csv`,
`report_long.md|csv`, `summary.md`.

## Что измеряем и критерии

| метрика | откуда | PASS | WARN | FAIL / блокер |
|---|---|---|---|---|
| RTF на файл (`total_ms / audio_ms`, включая загрузку моделей) | logcat `bench` | худший ≤ 0.5 | 0.5–1.0 | > 1.0 (запись дольше реального времени) |
| Разбивка по этапам (decode/vad/asr/diarization/align/llm) | logcat `bench` | — | этап > 50 % времени | — |
| Пик PSS процесса | `meminfo.csv` | ≤ 1.5 ГБ | 1.5–2.0 ГБ | > 2.0 ГБ (на 4 ГБ телефоне — LMK) |
| Пик RSS / VmHWM | `/proc/<pid>/status` | для справки; VmHWM — точный пик между сэмплами | | |
| Крэши, ANR, LMK, смена pid | `logcat.txt`, `meminfo.csv` | 0 | — | ≥ 1 |
| Валидность JSON (контракт AGENTS.md §2.4) | `validate_json.validate` в report.py/summary | 100 % OK | — | любой FAIL/MISSING |
| WER/DER на телефоне vs ПК (`artifacts/test-results/test_report.md`) | `report_main.md` | расхождение ≤ 1 п.п. | 1–3 п.п. | > 3 п.п. (другой декодер/числа/потоки) |
| Форматы: WER варианта vs wav-версии | `summary.md` | ≤ 1 п.п. | 1–5 | вариант не декодируется |
| Неречь (тишина/шум/музыка) | `summary.md` | 0 реплик | — | ≥ 1 реплики (правило 2.8) |
| Битый файл | `summary.md` | понятная ошибка в `error`, приложение живо | — | крэш процесса |
| Троттлинг | `thermal.csv` | status ≤ 1 | 2 | ≥ 3 — перемерить RTF на остывшем |
| Длинный файл 30 мин | `report_long.md`, `meminfo.csv` | без OOM, RTF как у коротких | fallback «один спикер» | крэш/LMK |

Ориентиры с ПК (`artifacts/test-results/test_report.md`): RTF 0.11–0.16, WER 0.9 % средний / 2.2 % худший.
Телефон ожидаемо в 3–5 раз медленнее; бюджет LLM = 0.3 × длительности (`PipelineConfig.llmBudgetFraction`)
сам по себе может дать до +0.3 к RTF.

Особенности интерпретации:
- BenchActivity создаёт движки на каждый файл: RTF каждого файла включает загрузку моделей, как у жюри.
- Первый файл после установки дополнительно копирует LLM (0.47 ГБ) в `filesDir` — его RTF записать отдельно
  (холодный старт). Порядок файлов в BenchActivity — по имени.
- `native_heap_mb` в строке bench — только нативная куча после файла; пик — по `meminfo.csv`/VmHWM.
- Для отчёта (DoD §6) записать: модель телефона, Android, RAM, SoC, `heapsize` — всё есть в `device.txt`/`summary.md`.

## Топ-5 рисков (red-team) и что делать

Оценка потерь — относительно 100 баллов при условии, что риск сработал на проверке жюри (3 файла).

| # | риск | как проявится в замере | потеря баллов | что делать |
|---|---|---|---|---|
| 1 | **OOM / LMK на 4 ГБ телефоне.** Одновременно в памяти: две ASR-модели по ~220 МБ (грузятся по очереди, но параллельно с диаризацией), диаризация держит весь сигнал во float в Java-куче (1 ч ≈ 230 МБ при `heapsize` 256–512 МБ), затем LLM 0.47 ГБ. `catch (Throwable)` в диаризации спасает только от `OutOfMemoryError` внутри неё; убийство процесса LMK не ловится ничем | пик PSS > 1.5–2 ГБ, строки `lowmemorykiller`/`has died`, смена pid, `CRASH` в `events.csv`, нет JSON для файла | файл без результата = WER/DER 100 % → до −25 за файл (≈ ⅓ от 75 баллов качества), плюс UX; при fallback «один спикер» — −8…−15 (DER) | прогнать `--long 30`; при PSS > 1.5 ГБ: выгружать ASR-модели до старта LLM (уже последовательно — проверить по `meminfo.csv`, где пик), уменьшить `numThreads` диаризации, блочная диаризация длинных файлов, LLM выключать при `MemAvailable` < 1 ГБ; убедиться, что fallback срабатывает (в logcat `diarization failed` вместо крэша) |
| 2 | **RTF > 1 на среднем CPU.** Два прохода ASR (слова + пунктуация), диаризация, LLM с бюджетом 0.3×длительности; на 4 ядрах `half` = 2 потока на ASR и диаризацию | RTF худший > 0.5, этап asr/llm доминирует в разбивке | скорость 10 баллов: от −3 до −10; при RTF > 1 жюри может прервать — тогда и качество | по разбивке этапов: уменьшить `llmBudgetFraction` (0.3 → 0.1) или выключать LLM по умолчанию, если WER с LLM не лучше; второй проход ASR только для пунктуации — сравнить WER/RTF без него; подобрать `numThreads` по `cpus` из `device.txt` (большие ядра) |
| 3 | **Первый запуск и установка 1 ГБ.** Нехватка места, долгая установка, копирование LLM 0.47 ГБ при первой обработке (жюри видит «зависший» первый файл), Android 14: FGS `dataSync`, уведомление без `POST_NOTIFICATIONS` | время установки, RTF первого файла заметно выше остальных, `INSUFFICIENT_STORAGE` | не установилось — 0 за всё; медленный первый файл — −1…−3 (UX/скорость) | в чек-листе засечь первый запуск на чистой установке; при большом отставании — копировать LLM в фоне при старте приложения и показывать этап «Подготовка модели»; README: требование к свободному месту |
| 4 | **Жизненный цикл UI.** Сворачивание/поворот/выход во время обработки; результат хранится в singleton `ProcessingRepository` — при гибели процесса в фоне теряется (на диске только `last_transcript.json`); протокол LLM в `remember` — при повороте пропадает, а нативный вызов продолжает работать (двойная LLM в памяти при повторном нажатии) | ручной чек-лист: пункты 6–8, 11 | UX 10 баллов: −2…−5; повторная обработка съедает время жюри | при провале: сохранять `Done` (путь к аудио + JSON) и восстанавливать при старте; `rememberSaveable` для протокола; блокировать кнопку «Протокол» до завершения предыдущего вызова |
| 5 | **Форматы и декодер устройства.** Жюри может дать m4a/ogg/opus/mp3 44–48 кГц стерео; MediaCodec на конкретном телефоне ведёт себя иначе, чем на ПК (bench на ПК не проходит через MediaCodec); amr/opus могут не декодироваться; длительность mp3/aac с priming-сэмплами сдвигает тайминги | `summary.md` → таблица форматов: вариант с ошибкой или WER vs wav > 1 п.п.; `end_ms > duration` | файл не декодируется — −25 за файл; сдвиг таймингов — −1…−3 (тайминги 10) | при ошибке: сообщение пользователю (не крэш) уже есть — проверить текст; для сдвига — сравнить `bnd_mean_ms` вариантов в `report_fmt.md`; при необходимости ресемплинг/даунмикс в своём коде вместо MediaCodec-выхода |

Вне телефона, но влияет на проверку: похожие голоса (DER ~50 % на `same_base`, см. LIMITATIONS.md) — «диалоги котиков»
могут быть стилизованными голосами; это не меряется этим планом, только `report_main.md` по ячейке `voices`.

## Что не проверено заранее (без телефона)

- Скрипт проверен `bash -n`, `--dry-run`, полным прогоном с фейковым adb (`.cache/fake_adb/`: имитация BenchActivity,
  крэш посреди прогона с перезапуском, ручной экспорт); формат реальных `dumpsys meminfo`/`thermalservice` проверен
  только на образцах — на конкретной прошивке поля могут называться иначе (тогда смотреть `meminfo_raw.txt`).
- Доступ `adb shell` к `/proc/<pid>/status` чужого приложения и к `/sys/.../scaling_cur_freq` зависит от прошивки
  (SELinux) — при отказе колонки пустые, PSS из `dumpsys` остаётся.
- `svc power stayon usb`, `wm dismiss-keyguard`, медиасканер (`--manual-push`) на некоторых прошивках не работают —
  тогда вручную: не гасить экран в настройках разработчика, разблокировать телефон.
