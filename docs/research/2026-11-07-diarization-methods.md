# Повторная кластеризация говорящих по эмбеддингам окон (2026-11-07)

Роль: speech-engineer. Задача: sherpa (pyannote-seg-3.0 + CAM++ + FastClustering, порог 0.5) и ClusterPost
сильно завышают число спикеров на живых голосах (DataHive: 2 человека → 6–25 кластеров). Нужно проверить
несколько способов исправить это в чистом Kotlin (`core`) поверх готовых турнов и эмбеддингов CAM++ окон, без новых моделей.
Критерий (AGENTS.md §9): пороги подбираются на dev (`dev` + `live_dev`), проверка на test (`test` + `live_test`).
Оцениваем лучшее среднее и лучший худший случай. Ни одна ячейка матрицы не должна стать хуже больше чем на 1 п.п.

## Что сделано
- `core/SymEigen.kt` — собственные значения и векторы симметричной матрицы: Хаусхолдер → трёхдиагональная матрица (tred2), затем неявный QL (tql2), порт EISPACK/JAMA. Режим «только значения» работает быстрее. Тесты `SymEigenTest`: Av = λv и ортонормированность до n = 200, след матрицы, два нулевых собственных значения у лапласиана графа из двух компонент.
- `core/Recluster.kt` — повторная кластеризация эмбеддингов окон (`ClusterPost.windows`, ≤ 40 окон на кластер, как в APK). Тесты `ReclusterTest` (12 шт.):
  - **NME** — спектральная кластеризация NME-SC: в аффинити оставляются p ближайших соседей, матрица бинаризуется и симметризуется, строится лапласиан L = D − A. p подбирается перебором 20 значений до 0.25·n по минимуму (p/n)/g_p, где g_p — нормированный максимальный eigengap. K = argmax eigengap, K ∈ [1, 8]. Дальше k-means++ (seed 0, 10 перезапусков) по K собственным векторам;
  - **SC** — то же с фиксированной долей соседей pval (вариант 3D-Speaker, с бинаризацией и без);
  - **AHC** — агломеративная кластеризация average linkage по косинусу. Три способа остановки: фиксированный порог; порог Оцу по распределению косинусов файла (адаптивный); максимум силуэта по K = 2..8 (**sil**), а если силуэт < silMin — K = 1;
  - постобработка меток: мелкие кластеры (< tinyMs / tinyFrac) переходят в ближайший центроид; сглаживание Витерби по времени (штраф за смену метки между соседними окнами с паузой ≤ 1 с);
  - **guard** (защита крупных кластеров): у старого кластера с ≥ `guardWindows` окон метка сохраняется. Такие кластеры уже проверил ClusterPost по ratio, а похожие голоса эмбеддинг всё равно не разделит. Окна мелких кластеров переходят в крупный кластер с той же новой меткой и ближайшим центроидом;
  - перенос меток на турны: `TURN` — по большинству окон турна, `WINDOW` — каждое окно своей меткой (турн может разделиться), `CLUSTER` — по большинству окон старого кластера (возможны только слияния);
  - если окон < 10 или старый кластер с окнами всего один (`minOldClusters` = 2), кластеризация не меняется. Так односпикерные файлы не дробятся;
  - `Recluster.afterClusterPost(turns, embs, cpCfg, rcCfg)` — шаг конвейера: ClusterPost, затем Recluster по тем же эмбеддингам.
- `core/ClusterPost.kt`: новый параметр `tinyWindows`. Кластер с числом окон меньше этого значения считается «мелким» и переходит в ближайший по голосу (метод 3 по числу окон). По умолчанию 0, то есть поведение не меняется.
- `bench/ClusterEmbeddings.kt`:
  - `--cp-max-windows` (для дампов без ограничения);
  - `--cp-recluster <ключи>` — то же, что в приложении: ClusterPost → Recluster;
  - в `cluster-sweep`: спецификация `x:m=nme|sc|ahc|otsu|sil,a=turn|window|cluster,guard=..,pre=0.97,tiny=..,tinyf=..,smooth=..,cap=..,minold=..`, хвост `:<cap>:<tinyWindows>` у `r:`-спецификаций, ограничение 40 окон на кластер как в APK, время Recluster в логе.
- `Bench.kt`, `Pipeline.kt`, `tools/`, `testdata/` не менялись.

Дампы (`--cp-dump`, свежий прогон, все окна): `out/dm_dump_{dev,test,live_dev,live_test}`. Результаты перебора лежат в `out/dmn_<set>/<метод>`. Baseline — **cp** (текущая конфигурация по умолчанию: sherpa th 0.5 + ClusterPost ratio 0.97, ≥ 3 окон). На свежих дампах cp воспроизводит TEST_RESULTS: live_dev 40.7 / 70.9, live_test 57.8 / 90.4.

## Что показали данные
- **Лишние кластеры на живых голосах — это фрагменты из 1–3 окон.** Например, в `dh_ru_000017` 28 кластеров: 10, 8, 5 окон, остальные по 1–3. ClusterPost их не сливает, потому что ratio требует ≥ 3 окон, а по 1–2 окнам within не оценить. Повторная кластеризация всех окон файла собирает их в 2–3 кластера.
- **Ratio cross/within не разделяет «тот же» и «другой» диктор в зоне 0.6–1.0.** Пары крупных кластеров одного живого диктора: 0.59–1.03. Разные дикторы: 0.13–0.5, но две женщины-актрисы (ls_masha_sveta) — 0.81–0.97, Piper — до 0.80, сдвиг высоты TTS — 0.89. Поэтому порог ratio ниже 0.97 вредит, а глобальная кластеризация всех окон работает лучше: решение принимается по всей структуре файла, а не по одной паре.
- **Выбор K.** Силуэт (AHC sil) устойчив: результат одинаковый при silMin 0.05–0.3. Чаще всего выбирается K = 2, и на живых данных это правильно. Однако на синтетике `speakers=5` без защиты он сливает три крупных кластера с разной высотой TTS в два: cpWER +42. Спектральная NME на test лучше всех (24.0 / 49.5) и не сливает 5spk, но на стилизованных голосах неустойчива: на live_test ff_stylized cpWER +17.9, худший DER live_dev 68.5. SC с фиксированным pval дробит разные голоса (distinct +74–107) — отвергнут. Фиксированный порог AHC (0.4 / 0.5) нестабилен между наборами (test speakers=3 +55 при 0.4), порог Оцу работает почти как силуэт.
- **Защита крупных кластеров (guard ≥ 15 окон) убирает катастрофу speakers=5 и почти ничего не стоит на живых данных.** live_dev 22.2 → 22.4. Плато guard 12–20 одинаково на dev и live_dev. При guard 8 на live_test speakers=3 cpWER +1.9: защищаются фрагменты одного диктора, поэтому 8 мало.
- **Перенос меток.** TURN и WINDOW на dev одинаковы (22.4 против 22.6). На live_test WINDOW лучше (31.6 / 61.9 против 32.8 / 65.6), потому что делит турны, в которых sherpa слила двух дикторов. По правилу выбора на dev оставлен TURN; WINDOW — равноценная альтернатива.
- **Сглаживание Витерби** не даёт выигрыша: штраф 0.1–0.2 меняет результат в пределах ±0.5, штраф 0.5 вредит (distinct_piper +23). Окна и так берутся из целых турнов, поэтому соседние окна одного турна почти всегда получают одну метку.
- **Метод 3 (мелкие кластеры → ближайший по голосу)** даёт примерно половину выигрыша: live_dev 30.8, live_test 50.9 при < 4 окон. Он падает на тех же ячейках, что и повторная кластеризация. Критерий «< 4 с речи» почти ничего не даёт на живых данных: фрагменты там по 5–40 с.
- **Ограничение 40 окон на кластер (как в APK) не влияет на результат**: с ограничением и без него метрики совпадают. Новых эмбеддингов не нужно.
- **Время**: Recluster sil на файл 3–5 мин занимает ≤ 7 мс на ПК (все 12 файлов — 15–19 мс), NME — до 55 мс (20 разложений). Память — матрица n×n, n ≤ 300.

## Проходит ли правило §9
**Ни один метод не проходит строго.** У всех методов, которые убирают фрагменты (метод 3, guard, повторная кластеризация), регрессируют одни и те же две синтетические записи:
- dev `clean_2spk_000` (same_base): «второй диктор» — это 8 с (2 окна) того же голоса TTS со сдвигом высоты. Он присоединяется к основному голосу: cpWER 87.6 → 96.3, DER 46.8 → 47.3. Ячейки voices=same_base +4.4, speakers=2 +2.4;
- test `clean_5spk_000`: кластер 8 с / 2 окна сливается с основным, cpWER 106.4 → 109.4 (+3.0 к худшему в speakers=5 и mixed). dev `clean_5spk_000`: три фрагмента по 1 окну (2–3 с), +2.0.

Это тот же артефакт набора, из-за которого в [cluster-post](2026-11-07-cluster-post.md) не включили `tinyMs`: варианты одного голоса TTS со сдвигом высоты CAM++ не различает (ratio 0.89–0.99). Живых «похожих голосов» в наборе нет, кроме ls_masha_sveta — а там рекомендуемый метод улучшает DER (ff_stylized live_dev 62.0 → 48.0, live_test 58.6 → 50.3). По DER у рекомендуемого метода нет регрессий больше 1 п.п. ни в одной ячейке ни одного набора. Ни один WER не меняется. Средняя ошибка границ растёт на файлах, где слились два похожих голоса (ff_stylized, same_base; см. таблицу границ выше). Это вторая цена метода.

**Рекомендация**: включить **sil + guard 15, TURN, после ClusterPost** как исключение из §9 с решением lead. Аргументы:
- выигрыш на всех реальных и стилизованных ячейках: live DER 50.5 → 16.9 (dev) и 66.0 → 29.3 (test), худший 70.9 → 22.7 и 90.4 → 41.7; mf_stylized 39.7 → 1.5;
- регрессии только на сдвиге высоты TTS (+2…+4.4 cpWER, DER не хуже);
- параметры на плато: guard 12–20 и silMin 0.05–0.3 дают одинаковый результат на dev.

Если исключение не принимается, то, чтобы строго выполнить §9, в `testdata` нужны настоящие похожие голоса (два живых диктора одного пола и возраста) вместо `same_base`/`mixed`, а затем повторить перебор (`cluster-sweep` по дампам — минуты).

Параметры: `Recluster.Config(method = AHC_SIL, assign = TURN, guardWindows = 15, minWindows = 10, minOldClusters = 2, silMin = 0.1, maxWindows = 300, minSpeakers = cfg.minSpeakers, maxSpeakers = cfg.maxSpeakers)`, остальное по умолчанию (tiny/smooth выключены).

## Что изменить в приложении (вносит lead)
1. `PipelineConfig` (core):
   ```kotlin

   val reclusterGuardWindows: Int = 15,
   ```

   ```kotlin
       if (cfg.reclusterEnabled) Recluster.Config(
           method = Recluster.Method.AHC_SIL, assign = Recluster.Assign.TURN,
   ```
