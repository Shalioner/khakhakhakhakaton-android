# Спайк: Nemotron-3-Diarization вместо pyannote-seg-3.0 + CAM++ + FastClustering (2026-11-07)

Роль: researcher. Все цифры ниже мы измерили сами на ПК, если не сказано иное. `[Проверить]` — не измерено.
Код спайка: `tools/spikes/nemotron_diarize.py`, `tools/spikes/nemotron_compare.py`, `tools/spikes/datahive_refs.py`. `src/` и `testdata/` не менялись.

## Вердикт (коротко)

**Внедрять, но как основной диаризатор с fallback на текущий стек, и только после замера на телефоне.**

- На **живых русских диалогах** (DataHive, 8 файлов, 2 собеседника, телефон/Opus) текущий стек разваливается: на сырых турнах он находит 11–55 «спикеров», DER 61.4 % в среднем и 82.0 % в худшем случае. После `core` получается 6–33 спикера и DER 75.9 / 112.7 %. У Nemotron на тех же файлах DER 14.5 / 36.6 % на турнах и 23.9 / 41.1 % после `core`, 2–4 спикера. Это главный аргумент. Русский язык в карточке модели не заявлен, но на деле она с ним работает.
- На синтетической матрице (Windows TTS) Nemotron не хуже нигде, кроме `clean_5spk` на dev. DER после `core`: dev 33.7 → 30.6 % в среднем, 60.1 → 51.0 % в худшем; test 27.6 → 24.3 % и 55.0 → 54.9 %. Отдельно: `clip` 60.1 → 36.4, `quiet` 46.1 → 29.7 (test), `snr8` 47.0 → 38.2 (dev). Регрессия на `dev/clean_5spk_000`: 32.0 → 50.1 %. Nemotron слышит там 2 голоса, потому что в синтетике всего 2 базовых TTS-голоса (Irina, Pavel), а остальные «дикторы» — их копии со сдвигом высоты. pyannote+CAM++ случайно режет эти сдвиги на кластеры. Значит, ось `same_base`/`mixed` нашей матрицы проверяет различение высоты одного TTS-голоса, а не разных людей. Регрессию надо учесть, но по правилу 9 она не опровергает вывод с живых записей.
- Порог кластеризации не нужен. Число спикеров модель определяет сама (до 8), а порог активности 0.5 из PR оказался оптимальным на dev (0.4–0.5 почти одинаковы).
- Скорость на ПК не хуже текущей диаризации, память умеренная: модель +144 МБ RSS, рабочая память около 65–100 МБ (подробно ниже).
- Условия внедрения: (1) RTF и RAM на телефоне укладываются в бюджет; (2) живой набор с 3–5 разными людьми не хуже текущего (сейчас 3–8 живых спикеров не проверены); (3) fallback (диаризация упала → pyannote+CAM++ → один спикер).

## 2. Реализация спайка

`tools/spikes/nemotron_diarize.py` — onnxruntime 1.31.1 (CPU), модели NealCaren. Всё повторяет эталонную numpy-реализацию PR #4032 (`test_onnx.py`, сверена с transformers: max diff 1.3e-5) и C++ `offline-speaker-diarization-sortformer-impl.h`. Ничего не подбиралось:
- фронтенд: преэмфаза 0.97 по всему сигналу; STFT center=True с нулевым паддингом 256; n_fft 512; **симметричное** окно Ханна 400 по центру 512; hop 160; |X|² @ Slaney-mel(128); `log(x + 2^-24)`; без нормализации; `num_frames = len // 160`;
- `num_embeds = num_frames // 8 + 1`: лишний кадр центрированного STFT, обнулён, но участвует в выходной свёртке, как в PR;
- шаг: `[кэш, FIFO, чанк + 40 кадров контекста]` → `step_int8.onnx`, позиции с нуля на каждом шаге; AOSC и FIFO с компрессией по score (`prediction_score_threshold` 0.25, boost 0.05, strong 0.75, weak 1.5, 1 «тихий» кадр на спикера) — перенос `SpeakerCache` из PR;
- постобработка как в PR `ComputeResult()`: порог 0.5, склейка пауз < `min_duration_off` 0.5 с, отброс турнов ≤ `min_duration_on` 0.2 с (значения из нашего `Bench.kt`);
- вход нормализуется так же, как в bench `WavReader`: DC-фильтр, ресемплинг до 16 кГц, громкость по речевым кадрам.

Единственное отличие от PR: в `step.onnx` NealCaren нет `attention_mask`. В последнем чанке при `num_frames % 8 == 0` нулевой хвостовой эмбеддинг не маскируется, это затрагивает последние около 80 мс файла. Замечено: int8 с динамической квантизацией чувствителен к шуму на входе. Пересчёт преэмфазы во float64 вместо float32 (разница log-mel 8e-5) сдвигал вероятности до 0.08, при этом решения совпали на 99.99 % кадров. PR сообщает до 0.2–0.23 относительно FP32.

Сравнение (`tools/spikes/nemotron_compare.py`, DER — `tools/der.py`, collar 250 мс, перекрытия учитываются):
- **cur_turns / nem_turns** — сырые турны диаризатора против эталона. Текущие турны взяты из дампа bench `--cp-dump` (строки T, до ClusterPost);
- **cur_e2e / nem_e2e** — после того же `core` (`TranscriptBuilder`: слова ASR → спикер, реплики), то есть то, что видит жюри. Для Nemotron турны в дампе заменены и прогнан `bench cluster-sweep <dump> <out> base=off`. `cur_e2e` — это `artifacts/test-results/*_report.csv`; пересчёт из дампов дал те же цифры.

Воспроизвести (модели в `.cache/models/nemotron/nealcaren/`, скачаны с HF):
```bash
python -I tools/spikes/nemotron_diarize.py --models .cache/models/nemotron/nealcaren --out out/nemotron/test \
    --cp-in .cache/nemotron/cp_dump_test --cp-out .cache/nemotron/cp_nem_test testdata/test/*.wav
java -cp <bench classpath> ru.neurosteno.bench.BenchKt cluster-sweep .cache/nemotron/cp_nem_test out/nemotron/sweep_test_nem base=off
python -I tools/spikes/nemotron_compare.py --split test --ref testdata/test \
    --sys "cur_e2e=csv:artifacts/test-results/test_report.csv" --sys "nem_e2e=json:out/nemotron/sweep_test_nem/base" \
    --sys "cur_turns=cp:.cache/nemotron/cp_dump_test" --sys "nem_turns=json:out/nemotron/test"
```
Дампы test и DataHive сняты нашим запуском bench (`--asr-dir models/asr_words --punct-dir models/asr --llm none --cluster-post on --cp-dump …`; ClusterPost меняет только выходной JSON, турны в дампе сырые). Дамп dev — копия `out/cp_dump_dev` от параллельного прогона.

| test quality=clean | 8 | 22.7 / 55.0 | 21.2 / 54.9 | 20.5 / 54.5 | 19.8 / 54.2 |
| test quality=clip / quiet / snr8 / tel8k | 1+1+1+1 | 34.5 / 46.1 / 32.4 / 36.3 | 31.0 / 29.7 / 31.7 / 30.1 | 28.3 / 40.6 / 29.5 / 31.2 | 28.3 / 28.3 / 28.3 / 28.3 |
| **DataHive real_ru** | 8 | 75.9 / 112.7 · 0/8 | **23.9 / 41.1** · 5/8 | 61.4 / 82.0 · 0/8 | 14.5 / 36.6 · 4/8 |

Как читать:
- **Синтетика не различает модели по главной оси.** Почти весь DER — `conf` на копиях одного TTS-голоса со сдвигом высоты: `same_base` и бо́льшая часть `mixed` (5 «дикторов» = 2 базовых голоса). Nemotron стабильно находит 2 базовых голоса. «Третий спикер» в `nem_turns` — ложный кусок короче 1 с (например, test/clean_3spk_000: 96.6 / 55.4 / 0.8 с), поэтому 8/12 «верно» на test случайно. `core` такие куски отбрасывает (`minSpeakerTotalMs` 1500), отсюда 5/12.
- **Главный выигрыш Nemotron — почти нулевой fa и устойчивость к искажениям** (clip, quiet, шум). pyannote+CAM++ дробит запись на лишние кластеры (до 8 на `snr8`), и `core` растягивает их в fa 5–10 %.
- **Регрессия по правилу 9**: dev `clean_5spk_000` +18.1 п.п. (32.0 → 50.1): pyannote отделил варианты высоты, Nemotron нет. На test тот же тип файла даёт 55.0 → 54.9. Записей, где 3–5 **разных** людей, у нас нет, и это главный пробел перед внедрением.
- **Живые записи** — единственное условие, где спикеры реально разные. Там текущий стек непригоден (десятки кластеров на 2 собеседника), а Nemotron даёт DER около 15 % на турнах. Большой miss у обоих (ru_000005/007: 30–35 %) — это, скорее всего, артефакт энергетического эталона (тихий канал, просачивание), а не диаризации. `[Проверить]` на ручной разметке.
- Порог активности (dev → test → DataHive, DER ср. на турнах): 0.4 → 28.0 / 23.3 / 14.1; **0.5 → 27.9 / 22.6 / 14.5**; 0.6 → 28.3 / 23.2 / 14.9. `min_on/min_off` 0.2/0.5 лучше, чем 0/0 (около −3 п.п.). Оставляем значения по умолчанию из PR и bench, ничего не подгоняем.

## 4. Скорость и память (ПК, Windows 11, 20 логических ядер, onnxruntime 1.31.1 CPU, int8)

**Важно:** во время замеров машину параллельно грузили другие прогоны bench (3–4 java-процесса до 800 % CPU), поэтому все RTF завышены и шумные. Сравнивать можно только цифры, снятые в одно время.

| что | RTF только диаризации | условия |
|---|---|---|
| текущая (pyannote+CAM++ 8 потоков), test, «тихий» прогон из `out/test_words/timings.json` | **0.060** | ранний прогон, нагрузка неизвестна |
| текущая, test, наш прогон под нагрузкой (`diar_ms` bench) | 0.153 | одновременно с Nemotron и чужими bench |
| текущая, DataHive под нагрузкой | 0.169 | то же |
| **Nemotron int8, 8 потоков**, test / dev / DataHive (по файлам) | **0.056 / 0.040 / 0.047** | под той же нагрузкой |
| Nemotron, 30 мин (склейка test), 8 потоков | 0.035 (первый замер 0.062) | под нагрузкой |
| Nemotron, 30 мин, **2 потока** | 0.054 (первый замер 0.074) | под нагрузкой |

Сложность Nemotron линейна по длине: один шаг на 27.2 с аудио, вход ≤ 684 энкодер-кадра. Оценка — около 160 GFLOP на шаг, то есть около 6 GFLOP на секунду аудио. У pyannote+CAM++ добавляется агломеративная кластеризация O(n²) по сегментам.

Память процесса Python (psutil, RSS):

| что | МБ |
|---|---|
| Python + numpy + onnxruntime до загрузки | 117 |
| после загрузки `embed.onnx` + `step_int8.onnx` | 261 (**+144** на модели) |
| прирост RSS во время диаризации, файлы 1–5 мин | **+64…65** |
| то же, 11 мин (DataHive ru_000003) | +92 |
| то же, 30 мин (сам массив аудио 115 МБ загружен до замера) | +101 (489 → 590) |
| пик процесса, 30 мин, включая аудио float32 | 591 |

Рабочая память модели ограничена окном (кэш 264 + FIFO 40 + 380 кадров). Рост с длиной файла — это массив вероятностей и турнов (8 float на 10 мс = 11.5 МБ/час) и аллокатор. Аудио целиком (16 кГц float32 = 230 МБ/час) нужно и текущему `diarizer.process(samples)`, так что разницы тут нет.

**Телефон (не измерено, `[Проверить]`):** публичных цифр RTF Nemotron на мобильном CPU нет (cassini-android их не публикует). Для текущего стека на Pixel 8 у Cassini (2 потока, pyannote+ERes2Net): RTF около 0.52, пиковый RSS 284 МиБ. По FLOP-оценке и ПК-замерам ожидаем для Nemotron int8 на 2 больших ядрах RTF 0.1–0.3, это не медленнее текущего, и RAM +250–350 МБ к процессу. На 4–6 ГБ телефоне это допустимо, если диаризация не идёт одновременно с LLM (llama.cpp около 470 МБ модели) и обоими ASR. Порядок этапов в сервисе уже последовательный по памяти `[Проверить]`.
