## Методика

- Конфигурация baseline = текущая по умолчанию: `--asr-dir …/asr_words --punct-dir …/asr` (два прохода ASR + PunctTransfer), `--llm none`, CAM++, `cluster-threshold 0.5`, VAD v4 из assets, `windowShiftRatio 0.1` (значение по умолчанию в `OfflineSpeakerSegmentationPyannoteModelConfig.Builder` sherpa-onnx 2.0.1 — проверено по байткоду), `chunkPadMs 200`.
- Новые опции bench (`Bench.kt`): `--decoding greedy_search|modified_beam_search`, `--max-active-paths N` (для обоих проходов ASR), `--window-shift-ratio R`, `--vad-model <onnx>`, `--chunk-pad-ms N`. По умолчанию поведение не меняется.
- Параллельно другой агент правил `core/` (SpeakerRelabel/TranscriptBuilder): первый прогон упал посередине (ClassNotFound) и дал несопоставимые baseline. Поэтому все цифры ниже — с **замороженной копией** `:bench:installDist` (состояние кода на 02:16, `--cluster-post` выключен), запуск `java -cp lib/* ru.neurosteno.bench.BenchKt` из корня. Baseline детерминирован: два прогона baseline (в начале и в конце серии) дали побайтово одинаковые JSON на dev и на test.
- RTF зашумлён параллельными прогонами на машине. На dev нагрузка падала по ходу серии (baseline в начале 0.161, в конце 0.111), поэтому RTF dev сравнимы только у соседних прогонов `vad62 / vad5 / pad500 / base2`. **Для скорости опорные цифры — test**: там нагрузка была ровной (base 0.113, base2 0.113).
- ПК x64, 8 потоков ASR/диаризации. RTF телефона не измерялся.
- Все значения — среднее / худшее, WER/cpWER/DER в %, границы в мс.

## Silero VAD: какие файлы и совместимость
- Текущий `assets/models/vad/silero_vad.onnx` (643 854 байт, sha256 `9e2449e1…`) — по метаданным ONNX это **silero-vad v4, экспорт k2-fsa, только ветка 16 кГц** (входы `x[1,512]`, `h`, `c`). Тот же файл, что `silero_vad.onnx` в релизе sherpa-onnx `asr-models`.
- v6.2: `https://raw.githubusercontent.com/snakers4/silero-vad/v6.2/src/silero_vad/data/silero_vad.onnx` (2 327 524 байт, sha256 `1a153a22…`, MIT). У тега v6.2.3 (2026-09-23, последний) файл побайтово тот же, новых весов после v6.2 нет. Лежит в `.cache/models/vad_alt/silero_vad_v6.2.onnx`.
- v5 от sherpa: `https://github.com/k2-fsa/sherpa-onnx/releases/download/asr-models/silero_vad_v5.onnx` (2 313 101 байт), `.cache/models/vad_alt/silero_vad_v5_sherpa.onnx`.
- Совместимость с `SileroVadModelConfig`: у v6.2 интерфейс v5 (входы `input`, `state[2,?,128]`, `sr`; выходы `output`, `stateN`). sherpa-onnx 2.0.1 (`silero-vad-model.cc`) определяет такую модель по 3 входам / 2 выходам (`is_v5_`), сам добавляет контекст 64 сэмпла и требует `windowSize = 512` — у нас 512. На dev, test и злых файлах всё отработало без ошибок. Подменить файл в assets можно без изменений кода.
- Почему v5/v6.2 хуже на границах: при тех же `threshold 0.5 / minSilence 0.3 с` новые модели склеивают короткие паузы в более длинные сегменты. Например, на `mono_1spk_000` (dev) получается 7 реплик вместо 8, и ошибка границ растёт на 0.6–1 с. Сравнивать v6.2 честно можно только после своего подбора `vadThreshold` / `vadMinSilenceSec` на dev — это отдельная задача.

## Предложения (код приложения не менялся)
1. `EngineConfig` (`engine-sherpa/SherpaEngines.kt`): декодер оставить `greedy_search` (в `SherpaAsr` сейчас задан строкой). Поле для beam search не добавлять.
2. `EngineConfig`: добавить поле `segWindowShiftRatio: Float = 0.1f` и передавать его в `OfflineSpeakerSegmentationPyannoteModelConfig(model = …, windowShiftRatio = cfg.segWindowShiftRatio)` в `SherpaDiarizer`. Сейчас там неявно стоит 0.1 из sherpa. **Значение по умолчанию оставить 0.1.** 0.2 вернуть на повторный A/B **вместе с подбором `clusterThreshold` / ClusterPost** (задача агента cluster cleanup): выигрыш RTF −25 % реальный, но сейчас 0.2 сдвигает число кластеров на пограничных файлах. Это проблема устойчивости кластеризации, а не самой сегментации.
3. `ModelAssets.VAD`: оставить v4. Если пробовать v6.2 дальше, то только вместе со свипом `EngineConfig.vadThreshold` (0.5 / 0.6 / 0.7) и `vadMinSilenceSec` на dev. Принимать при условии, что границы на mono/clean не хуже текущих. Проверка на test показала, что потенциал по WER есть (0.9 → 0.5).
4. `PipelineConfig.chunkPadMs`: оставить 200.
