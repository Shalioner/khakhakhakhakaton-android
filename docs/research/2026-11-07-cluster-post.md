# Постобработка кластеров диаризации по эмбеддингам (2026-11-07)

Роль: speech-engineer. Задача: FastClustering sherpa-onnx (complete linkage, один порог) ошибается в числе спикеров. Нужно улучшить DER/cpWER постобработкой кластеров так, чтобы ни одна ячейка dev не ухудшилась больше чем на 1 п.п. (по среднему и по худшему случаю), и подтвердить результат на test.

## Что сделано
- `core/ClusterPost.kt` — чистая логика, тесты в `ClusterPostTest` (10 шт.):
  - `windows(turns)` — части турнов, не перекрытые другими кластерами, нарезанные на окна 1–6 с; не больше 40 окон на кластер, выбираются равномерно по времени;
  - статистика кластера — сумма S и число n нормированных эмбеддингов окон. Из неё `cross(i,j) = S_i·S_j/(n_i n_j)` (средний косинус между окнами двух кластеров) и `within(i) = (|S_i|²−n_i)/(n_i(n_i−1))` (средний косинус внутри кластера);
  - агломеративное слияние пары с максимальным `ratio = cross/within`, пока ratio > `mergeRatio`. В слиянии участвуют только кластеры, у которых ≥ `minWindowsForMerge` окон. Смысл: окна одного кластера похожи на окна другого так же, как друг на друга, то есть эмбеддинг эти кластеры не различает. Критерий относительный и подстраивается под условия записи (шум, 8 кГц) лучше фиксированного косинуса;
  - есть и выключены: слияние по косинусу центроидов (`mergeCos`) и перенос мелких кластеров (< `tinyMs` / `tinyFrac`) в ближайший по голосу кластер, как `min_cluster_size` в pyannote.
- `engine-sherpa/SherpaClusterEmbedder` — `SpeakerEmbeddingExtractor(assets, config)`, `createStream/acceptWaveform/inputFinished/isReady/compute`. Аудио читается окнами из `PcmFile`.
- `app/Pipeline.kt` — после диаризации (диаризатор уже освобождён) загружается извлекатель. Он считает эмбеддинги, применяется `ClusterPost`, и извлекатель сразу закрывается. Если что-то падает, остаются исходные турны и выводится предупреждение. Шаг управляется флагом `PipelineConfig.clusterPostEnabled`.
- `bench/ClusterEmbeddings.kt` — то же через Java API (`--cluster-post on`, `--cp-ratio`, `--cp-merge`, `--cp-tiny-ms`, `--cp-tiny-frac`, `--cp-dump <dir>`). Режим `bench cluster-sweep <dump_dir> <out_root> name=<c|r>:<порог>:<tinyMs>:<tinyFrac>[:<minWindows>][@minSpeakerMs]` перебирает пороги по дампу (турны, слова, VAD, эмбеддинги), не пересчитывая ASR и диаризацию. `Bench.kt` изменён в 4 местах по одной строке.

## Что показали данные (dev, CAM++)
Анализ дампа: окна сопоставлялись с эталонными спикерами по перекрытию.
- Разные базовые голоса TTS (Irina и Pavel): `cross` ≈ 0.24–0.31, `within` ≈ 0.76–0.82, ratio ≈ 0.3.
- Варианты одного голоса со сдвигом высоты (`same_base`/`mixed`): косинус центроидов 0.80–0.93, ratio 0.89–0.99. Эмбеддинг их не различает, поэтому sherpa сливает таких дикторов в один кластер с примерно равными долями (purity ≈ 0.51). Постобработкой, которая только сливает кластеры, это не чинится.
- Лишние кластеры: `clip` (3 спикера → 6 кластеров, из них 4 принадлежат speaker_3, ratio 0.94–1.03), `noisy` (3 → 8, четыре одиночных окна по 1–2 с от speaker_3). Это и есть исправимая часть ошибки.
- Слияние по фиксированному косинусу центроидов не работает: пары «тот же диктор» (0.65–0.91) и «разные похожие дикторы» (0.80–0.93) перекрываются. При пороге 0.80–0.85 cpWER на speakers=5 вырастает на 38–40 п.п.
- Слияние по ratio без минимума окон сливает `clean_2spk_000` (ratio 0.986, у меньшего кластера 2 окна) в одного спикера: cpWER +8.7. Минимум 3 окна на кластер (оценка `within` по 1–2 окнам ненадёжна) это блокирует.
- `computeConfidence` из FastClusteringConfig не использовался. Это силуэт на эмбеддингах 10-секундных чанков sherpa, а ratio — та же идея на уровне кластера, но на длинных чистых окнах без перекрытий и без изменений в конфиге диаризатора.

## Решение
- **По умолчанию включено**: `clusterPostEnabled=true`, `clusterPostMergeRatio=0.97`, `clusterPostMinWindows=3`. На dev и test нет регрессий ни в одной ячейке (0.0 п.п.), среднее и худший DER улучшаются.
- **Мелкие кластеры по голосу — выключено** (`clusterPostTinyMs=0`). Это лучшая по среднему конфигурация (dev DER 31.7, cpWER 56.5; на test без регрессий), но на dev speakers=5 cpWER вырос на 2.0 п.п.: два чистых кусочка speaker_1 по 1.6 с ушли в кластер, где speaker_1 и speaker_4 уже слиты (голоса `same_base`). Включать стоит после того, как в наборе появятся настоящие похожие голоса вместо сдвига высоты TTS.
- Перенос мелких кластеров по эмбеддингу явно лучше переноса по времени (`minSpeakerTotalMs` 3000: DER на tel8k +6.9). Текущий `absorbTinySpeakers` (1.5 с) оставлен как есть.
- В `bench` шаг включается явно: `--cluster-post on`. По умолчанию он пока выключен, чтобы не сдвинуть baseline параллельного A/B опций sherpa. Для паритета с APK после этого A/B флаг нужно включить в стандартных прогонах.

## Стоимость
- ПК, загружен параллельными прогонами: 1.5–2.2 с на файл 1.5–3 мин (20–48 окон), то есть около +0.01 RTF. Собственный этап эмбеддингов sherpa на тех же файлах занимает 7–28 с: окна у нас не перекрываются, а у sherpa сдвиг 1 с при окне 10 с.
- Память: модель CAM++ (~30 МБ) грузится после освобождения диаризатора. На файл больше 40 окон на кластер не считается, то есть не больше 4 мин аудио на кластер даже для часовой записи.
- **На телефоне не измерено** `[Проверить]`.

## Ограничения
- Шаг только сливает кластеры и не умеет их разделять. Основная ошибка на синтетике (`same_base`/`mixed`: два диктора с одним базовым голосом TTS в одном кластере) остаётся: CAM++ такие голоса не различает (ratio ≈ 0.9–1.0). Для этого нужна сегментация, которая различает дикторов внутри чанка (cannot-link между локальными спикерами одного окна), или end-to-end диаризация. Ни то, ни другое не доступно через Java/Kotlin API sherpa-onnx 2.0.1.
- Выборка маленькая (12+12 синтетических файлов). Эффект пока держится на двух файлах (clip, quiet).
